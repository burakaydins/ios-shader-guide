## 1. Cost model

- A shader runs **for every pixel** in the area the effect is applied to. On a Retina screen, full screen means millions of invocations; cost = number of pixels × operations inside the shader.
- By Apple's definition `layerEffect` runs on a raster layer created from the view; a layer cost is also expected for `distortionEffect` and `colorEffect`, but this was not verified when the skill was written. Every extra effect can add layer and memory cost; keep the chain short and measure.
- Expensive: loops (raymarching, multi-octave `fbm`), many `layer.sample` calls (24 in glow), piles of `pow`/`exp`/`sin`, heavy texture sampling.
- Cheap: `mix`, `step`, `smoothstep`, `fract`, basic arithmetic.

## 2. Speed-up checklist

From largest to smallest effect, in the order to try:

1. **Shrink the area.** Apply the effect to the smallest view needed (a card, a badge) instead of full screen.
2. **Lower the frame rate.** For slow ambient effects use `AnimatedShader(fps: 30)` or 24 (`swift-patterns.md` section 1).
3. **Stop unneeded work.** If the effect is not visible give `isEnabled: false` or pause the `TimelineView` (`paused:`). Stop the animation when it leaves the screen.
4. **Leave static effects without animation.** If it does not depend on time, do not use `TimelineView`; the shader re-runs only when the view changes.
5. **Shorten loops.** Drop `fbm` octaves from 5 to 3, raymarching steps from 48 to 32, and compare by eye.
6. **Move computation to Swift.** Values that are the same for every pixel (constant factors, `sin(time)`) can be computed once on the CPU and passed as uniforms.
7. **Use `half`.** `half` for color math, `float` for position/time math (see `msl-primer.md` section 4).
8. **Reduce branching.** If neighboring pixels take different branches the GPU may run both; `mix`/`step`/`select` are often better. The effect of this rule varies by shader; measure.
9. **Draw at low resolution.** Applying a heavy background to a half-size view and enlarging it with `scaleEffect(2)` is cheap but looks soft/blurry. This method was not tried when the skill was written.
10. **Be careful in lists.** In scrolling list cells `layerEffect`/`distortionEffect` can be expensive (one raster layer per cell). Measure first with a small list.

## 3. Measuring

- Measure on a real device, not the Simulator.
- For line-by-line cost and variable values there is Xcode's Metal debugger (section 9). Apple's articles do not mention SwiftUI shaders specifically; whether SwiftUI shaders appear as a separate draw command in a capture was not verified when this skill was written. Try it and share the result with the user.
- First **remove** the shader (`isEnabled: false`) and measure the frame rate, then turn it on: the difference is the shader's cost.
- Do not say "it runs at 60 fps" or "it is slow" without measuring; ask the user which device they measured on.
- If you see a hitch on the first frame, try precompiling the shader (`Shader.compile(as:)`, see `swiftui-shaders.md` section 10).

## 4. Heat, battery, accessibility

- A continuously animated full-screen effect drains the battery and heats the device. Do not run it continuously unless truly needed; short animations (0.3–2 s) are a good default.
- Low Power Mode: if `ProcessInfo.processInfo.isLowPowerModeEnabled`, lower `fps` or turn the effect off.
- Thermal state: if `ProcessInfo.processInfo.thermalState` is `.serious`/`.critical`, simplify heavy effects.
- Respect the "Reduce Motion" setting (`AnimatedShader` does). Turn off flashing, fast-moving effects (glitch) in particular.

## 5. Debugging with color

There is no `print` inside a shader. The method is to **turn the value you want to see into a color**:

```metal
// Debug by color: apply one of these in place of your effect to SEE a value.
// Swift:  content.colorEffect(ShaderLibrary.debugUV(.float2(proxy.size)))

[[ stitchable ]] half4 debugUV(float2 position, half4 color, float2 size) {
    float2 uv = position / size;                       // red = x, green = y, origin top-left
    return half4(half(uv.x), half(uv.y), 0.0h, 1.0h);
}

[[ stitchable ]] half4 debugAlpha(float2 position, half4 color) {
    return half4(half3(color.a), 1.0h);                // white = opaque, black = transparent
}

// Shows a number as a gray ramp: 0 -> black, 1 -> white. Magenta = NaN or inf.
// Pass your computed value as `value` from a copy of your shader to inspect it.
static inline half4 debugRamp(float value) {
    if (!isfinite(value)) { return half4(1.0h, 0.0h, 1.0h, 1.0h); }
    return half4(half3(half(saturate(value))), 1.0h);
}

[[ stitchable ]] half4 debugGrid(float2 position, half4 color, float spacing) {
    // distance (in points) to the nearest grid line
    float2 g = abs(fract(position / spacing + 0.5f) - 0.5f) * spacing;
    float lineMask = 1.0f - smoothstep(0.0f, 1.0f, min(g.x, g.y));
    return mix(color, half4(1.0h, 0.2h, 0.2h, 1.0h), half(lineMask));
}
```

Usage examples:

```swift
// is uv correct? top-left should be black, bottom-right yellow, top-right red, bottom-left green
content.colorEffect(ShaderLibrary.debugUV(.float2(proxy.size)))

// where does alpha come from?
content.colorEffect(ShaderLibrary.debugAlpha())

// a 50-point coordinate grid
content.colorEffect(ShaderLibrary.debugGrid(.float(50)))
```

To see your own value, change a copy of the shader so it returns `debugRamp(value)`. Rules:

- **Bisect.** Turn half of the effect into a constant color; split whichever half has the problem.
- **One value at a time.** Verify separately that `time`, `size` and the touch point arrive correctly by viewing e.g. `debugRamp(time / 10.0)`.
- **Check the uniforms.** When in doubt, write the Swift argument order and the MSL parameter order side by side and compare.

## 6. Compile error dictionary

| Error text (summary) | Meaning and fix |
|---|---|
| `no matching function for call to 'mix'` (or `clamp`, `max`...) | Argument types do not match, often a `half3` / `float3` mix. Convert one explicitly: `float3(h)` / `half3(f)` |
| `cannot initialize a variable of type 'half4' with 'float4'`-like | Same cause; convert with `half4(f)` |
| `use of undeclared identifier 'X'` | A typo, or the function is defined after where it is used (move it up), or an `#include` is missing |
| `unknown type name 'Layer'` / `'SwiftUI'` | `#include <SwiftUI/SwiftUI_Metal.h>` (or `<SwiftUI/SwiftUI.h>`) is missing; the `layer` parameter must be `SwiftUI::Layer layer` |
| `redefinition of 'X'` / duplicate symbol | Two `.metal` files declare a function with the same name; make the shared helper `static inline` and put it in a `.h` |
| `recursive function call is not supported` | Recursion is forbidden; turn it into a loop |
| `variable length arrays are not supported` | The array size must be a compile-time constant |
| `address space` related error | Globals must be `constant`; there are no written globals (`msl-primer.md` section 5) |
| `invalid operands to binary expression` | Vector sizes do not match (`float2 + float3`) |
| `ambiguous` call | A mix of integer and real numbers; add an `f` suffix to literals (`2.0f`) |

The error comes with a line number; in Xcode's build output, MSL errors take you to that line when you click the `.metal` file.

## 7. "Effect not showing" decision tree

1. **Did the build pass?** If not, section 6.
2. **Is the name exactly the same?** `ShaderLibrary.plasma` ↔ `plasma` (case-sensitive). The compiler does not check the Swift-side name.
3. **Is `[[ stitchable ]]` there?** If not, the function is not found.
4. **Do parameter order and count match?** `position` first; then `color` or `layer`; then the arguments you pass from Swift *in the same order and type*. An array argument takes two parameters.
5. **Is it the right modifier?** It must match the signature type: `colorEffect` ↔ `half4 f(position, color, ...)`, `layerEffect` ↔ `half4 f(position, Layer, ...)`, `distortionEffect` ↔ `float2 f(position, ...)`.
6. **Is there a placeholder / pink image?** The view may be backed by UIKit/AppKit (`swiftui-shaders.md` section 9).
7. **Is it returning alpha 0?** Look with `debugAlpha`. A `colorEffect` applied to a fully transparent base may not work as you expect; try an opaque base (`Rectangle().fill(.black)`).
8. **Are the parameter values reasonable?** `amplitude` may be 0.0001 or the frequency 0. See the values with `debugRamp`.
9. **Is `isEnabled` true?** For touch effects the `isEnabled` condition may never be satisfied (`swift-patterns.md` section 3).

## 8. `NaN`, `inf` and fast math

- `normalize(float2(0))`, `0.0 / 0.0`, the `sqrt` of a negative number, `pow(negative, fractional)` produce `NaN`; the result is typically black or wrongly colored pixels. Guard before normalizing a zero-length vector (the `ripple` recipe does this).
- In the Metal compiler fast math may be on by default; when it is on, `NaN`/`inf` comparisons and `isnan` results may be unreliable. Check the Metal fast math option in the Xcode build settings; its value was not verified when this skill was written.
- The `isfinite` check inside `debugRamp` can be inconsistent when fast math is on; if you suspect a `NaN`, guard the value with `clamp` or `max(x, 0.0001)` and see whether the result changes.

## 9. The Xcode Metal debugger: inspecting a shader line by line

The steps in this section come from these Apple articles: "Inspecting shaders", "Capturing a Metal workload in Xcode", "Building your project with embedded shader sources" and "Debugging the shaders within a draw command or compute dispatch". Menu names can vary with the Xcode version. **None of these articles mention SwiftUI shaders**; try for yourself how a SwiftUI shader shows up in a capture.

### 9.1 Setup (once)

1. **Embed source code in the build.** Project ▸ Build Settings ▸ Metal Compiler Build Options ▸ **Produce Debugging Information**: set the *Debug* entry to **"Yes, include source code"**. Apple reminds you to set this to **No** for *Release* when debugging is done, otherwise debug information goes into the app you ship. If you capture without embedding the source, the Shader editor and shader debugger do not work properly.
2. **Turn on GPU Frame Capture.** Scheme menu ▸ Edit Scheme ▸ **Run** ▸ **Options** tab ▸ **GPU Frame Capture**: *Automatically*, *Metal* or *Disabled*. If your target links Metal (or a framework that uses Metal), Xcode turns it on by itself; in shared projects someone may have turned it off. *Disabled* is for measuring peak performance (capture adds a small but measurable CPU cost).

### 9.2 Capturing

1. Run the app on a device from Xcode.
2. Click the **Metal Capture** button in the debug bar.
3. Choose the **Scope** (frame, Metal layer, command queue, device or a custom scope), choose the count, and press **Capture**. To stop manually, **Finish**.
4. In the popover's *Advanced* section the **Profile after replay** option produces a profile automatically after the capture is replayed. Apple says this slows the debugger at startup; turn it on only when examining performance.
5. To save the capture use **File ▸ Export** (it becomes a GPU trace file).

### 9.3 Finding a bug in a shader (the shader debugger)

1. In the Debug navigator select the **draw command** you are interested in.
2. Click the **Shader Debugger** button in the debug bar. The window that opens has a tab for each shader type (Vertex, Fragment...). To examine a pixel of a SwiftUI effect, pick a pixel in the **Fragment** tab and press **Debug**.
3. In the call tree the **down/up arrows** step forward/back, the **right arrow** steps in, the **left arrow** steps out. The green highlighted line is the "playhead".
4. Unlike the CPU debugger, the **values of all variables** appear next to the lines at once; there is no need to step through one by one. Hovering shows detail. If you open the Preview the values appear inline.
5. In loops, the **Loop Iteration** tab lets you choose which iteration's values to see (very useful for fbm or raymarching).
6. The neighbors of the pixel you chose are shown too (*region of interest*); if you expand a variable you can visually compare the values of all pixels in this region. In the mask, pixels that run that line are white and those that do not are black; this shows on which pixels branching diverges.
7. After fixing the shader, refresh the captured frame with the **Reload Shaders** button. **Important:** these changes apply only inside the debugger; you need to copy the fix into your own `.metal` file by hand.

The debugger does not replace color tricks like `debugUV`/`debugRamp` (section 5) but is powerful with them: catch the suspect variable with color first, then read its exact value in the debugger.

### 9.4 Seeing cost line by line (profile)

- If you took the capture with **Profile after replay**, or press the **Generate** button at the top right of the Shader editor, numbers appear for every line of the shader. On GPU family 4 and later Apple also shows a pie chart next to the numbers; hovering enlarges the detail.
- GPU work is divided into four categories: **memory, ALU, synchronization, control flow**. Apple's recommendations:

| Category | What it means | Apple's recommendation |
|---|---|---|
| ALU | Time spent in the arithmetic unit | Use `half` instead of `float` where possible; reduce complex instructions such as `sqrt`, `sin`, `cos`, `recip` |
| Memory | Waiting for buffer/texture memory | Shrink textures; if little time is spent in memory you can raise texture resolution |
| Control flow | Branching, loops, jumps | Use a **constant iteration count** in loops; the compiler can then produce optimized code |
| Synchronization | Waiting for resources/events (texture sampling, pixel, barrier, atomic subtypes) | Varies by subtype; "wait memory" is tied to texture/buffer access |

- These recommendations overlap with the list in `performance-debugging.md` section 2 (constant loop count, `half`, reducing expensive functions).
- **For current numbers** temporarily set the app's deployment target equal to the device's OS version; if they do not match, the Shader editor shows a warning. Do not forget to restore the old value when done.
- **For consistent results** pick a fixed performance state from the **GPU Profiler** button in the debug bar; it reduces run-to-run variation.
